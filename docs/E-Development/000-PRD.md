## 3. Trust-band × reporter-badge system

The single most load-bearing architectural decision. Per `01-design-system-foundation.md` §3 + `decisions/00-lockdown-audit.md` §5:

### 3.1 Trust band = verification state

| Band | Meaning | Semantic |
|---|---|---|
| **T1** | Unverified (divider) | First receipt, no verification yet |
| **T2** | Verified | On-site confirmation or PHA-corroborated |
| **T3** | Issuance (consumer notice) | Reserved for public-notice path; build-time lint-enforced |
| **resolved** | Closed | Lifecycle end state |

CSS tokens: `--color-trust-t1`, `--color-trust-t2`, `--color-trust-t3`. See `01-design-system-foundation.md` for hex values.

### 3.2 Reporter badge = source attribute (separate dimension)

| Badge | Source |
|---|---|
| `anchor` | Trusted citizen (Anjali-type) |
| `hotline` | Telephone hotline intake |
| `webform` | Submit Report web portal |
| `sensor` | IoT/sensor wire format |

CSS tokens: `--color-reporter-anchor`, `--color-reporter-hotline`, `--color-reporter-webform`, `--color-reporter-sensor`.

### 3.3 Cross-product rule

> A reporter can be an anchor at any trust band.
> Hotline-sourced = T1 default + hotline reporter-badge (NOT T3).
> T3 is reserved for consumer-notice issuance path; never applied to incoming reports.

This separation lets:
- Anchor citizens render their badge regardless of verification.
- Hotline-sourced incidents render their source badge regardless of band.
- Pia (Phase 2) drill on either dimension independently in Scenario 05.
- Build-time lint to enforce T3 reservation.

## 4. Authentication & session

### 4.1 Current state (Phase 1)

- Mock auth via MSW handlers (`web/src/mocks/handlers.ts`).
- `idb-keyval` persists session across reloads.
- Session-bus event pattern: `surakkha:session-changed` (see `web/src/mocks/session-bus.ts`).
- `<RequireSession>` listens for the event and re-reads `getSession()`.

### 4.2 Roles

| Role | Routes |
|---|---|
| utility_operator | `/dashboard`, `/inbox`, `/inbox/:id`, `/verify-flow`, `/audit-log`, `/settings` |
| field_technician | `/field/*` |
| citizen | `/submit`, `/my-reports/:incident_id/timeline` |
| pha_approver | `/approve` |
| pha_viewer | `/audit` |
| vendor | `/vendor` |

All authenticated routes are wrapped in `<AppLayout>` (FE-1.6a). `/`, `/login`, and `/styleguide` live outside the chrome.

### 4.3 Logout contract

- `POST /api/auth/logout` resets session.
- IDB key cleared.
- Catch-all `<Navigate to="/" replace />` lands users on login.

### 4.4 Migration target (when backend lands)

- Replace MSW handlers with real `/api/auth/*` endpoints.
- Session storage moves to httpOnly cookies + CSRF token.
- Same `RequireSession` listener pattern works; only the storage layer changes.

## 6. Chain-verification utility

### 6.1 Status

`web/src/lib/chain-verify.ts` exists. Used by `AuditLog` and `InboxDetail`. Spec §10 mandates <200 ms verification with 1500 ms client-side abort timeout.

### 6.2 Public contract

```ts
type VerifyState =
  | { status: 'idle' }
  | { status: 'pending' }
  | { status: 'ok' }
  | { status: 'fail'; reason: 'unknown_hash' | 'hash_mismatch' | 'network' | 'timeout' };

verifyBlock(block_hash: string): Promise<VerifyState>;
```

### 6.3 Hard rules

- **Never throws.** Failures degrade gracefully — the calling component renders a stable shape.
- **Single source of truth.** Both `AuditLog` and `InboxDetail` import this helper; do NOT copy-paste the verify logic.
- **Future:** `IncidentChainSegmentPage` (Tier 1 spec, WO-003) MUST import this helper. Spec §10 binding.

### 6.4 Wire contract

- `POST /api/chain/verify` with `{ block_hash }` body.
- Server recomputes canonical SHA-256 over the block's stored fields and compares.
- Response: `{ ok: true } | { ok: false, reason }`.

## 7. Mock API contract (current)

`web/src/mocks/handlers.ts` — 875 LOC, 30+ routes. Until backend lands, all features must respect this contract.

### 7.1 Auth

- `POST /api/auth/login { persona_id }` → `SessionRow`
- `POST /api/auth/logout` → `{ ok: true }`
- `GET /api/auth/me` → `SessionRow | 401`
- `GET /api/auth/personas` → `Persona[]`

### 7.2 Chain

- `GET /api/chain/head` → `Block | 404 chain empty`
- `GET /api/chain/blocks?from=…&to=…` → paginated blocks
- `POST /api/chain/verify { block_hash }` → `{ ok } | 404 unknown_hash | 400 missing_block_hash`

### 7.3 Events

- `POST /api/events` → emit chain event (requires session; 401 if absent)

### 7.4 Stability rule

When a feature PRD describes new endpoints, it MUST add them to `handlers.ts` + `fixtures.ts` + `canonical.ts` together. No half-built mocks.

## 11. Cross-cutting concerns

### 11.1 Logging & telemetry

- All chain reads (verify, fetch blocks, fetch head) MUST be logged for the audit log (PR 4 in the 95-step plan).
- No PII in client-side logs; session-id is sufficient.
- ErrorBoundary + ErrorScreen + ToastProvider cover the user-visible error surface.

### 11.2 Audit

- `AuditLog` page reads from `/api/chain/blocks` + session events.
- Reporter-badge is recorded as a separate chain-event field (not derived from trust band).
- `surakkha:session-changed` event bus is the single mutability point for session state.

### 11.3 Accessibility (a11y)

Per lockdown: WCAG AA compliance enforced.

- `jsx-a11y` ESLint plugin enabled.
- Keyboard navigation: all interactive elements reachable via Tab.
- ARIA labels: every interactive element gets `aria-label` from the spec's Area Label table.
- Focus management: Modal/Dropdown/Tooltip all implement focus traps.
- Bangla font loading: documented in `02-typography-lockdown.md`.

### 11.4 Error handling

- ErrorBoundary catches render errors.
- ToastProvider surfaces transient errors.
- ErrorScreen handles app-level failures.
- `chain-verify.ts` never throws — degrades to typed `VerifyState`.

### 11.5 Performance budgets (from foundation §12)

- Initial route render: <200 ms (mock).
- Chain verify: <200 ms.
- Bundle size: monitor via `pnpm build` (Vite default chunking).
- No SSR; pure CSR SPA.

## 13. Feature PRD authoring contract

Per WDS `wds-glossary.md` + `saga/SKILL.md`:

### 13.1 File naming

- `NNN-[feature].xml` (zero-padded, hyphenated).
- One per Work Order.

### 13.2 Required sections (every feature PRD)

1. **Objective** — single sentence from the parent WO.
2. **Scope** — what's in, what's out.
3. **Parent artifacts** — pointers to spec(s), scenario(s), WO.
4. **Acceptance criteria** — testable, derived from spec acceptance rules.
5. **UI rules** — Area Labels (per `01-design-system-foundation.md` §13), component primitives used, theme tokens.
6. **Wire contract** — mock endpoints added/touched (with handler updates required).
7. **i18n keys** — new EN + BN keys added (with key parity).
8. **Tests required** — vitest feature checks + any playwright spec updates.
9. **Migration debt** — any known `--band-*` → `--color-trust-*` migrations.
10. **Lockdown compliance** — explicit confirmation that all 5 lockdown decisions are respected.

### 13.3 Conflict resolution

- Lockdown spine > this document > feature PRD > spec.
- Within a spec, the section-most-specific rule wins.

## 15. Living-document rule

This PRD is updated when:

- A lockdown decision changes (rare; cascades through foundation + specs).
- A new cross-cutting concern emerges (e.g., a new domain enum in `types/domain.ts`).
- A new primitive is added to `web/src/components/ui/`.
- The mock API surface changes (new `/api/*` endpoint families).

It is NOT updated for:

- Per-feature behavior (lives in feature PRD).
- Per-page UI rules (lives in spec).
- Per-component implementation (lives in code).
