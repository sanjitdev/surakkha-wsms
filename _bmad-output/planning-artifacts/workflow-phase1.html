Beautifully orchestrated incident lifecycle · 5 epics · ~17 stories · 15 chain events · trust scoring pre-triage
Phase 1 MVP Single-city Dhaka Three personas: Admin / Operator / Anjali-Sensor Audit chain as state

1. At a glance

Three personas, eleven core chain events (plus four trust-system events), twelve states. The incident's lifecycle is derived from the chain, not stored in a status column. Every notification is a chain event. Every SLA is on a timer. Every gate (verify, assign, dispatch, resolve) emits an event before the next one fires. The system pre-triages; the admin overrides. The chain is the audit trail; the projection is what each persona sees.

4. Chain events (the spine)

Fifteen first-class event types. Eleven gate events + four trust-system events. Every state transition emits exactly one. The order in the chain is the order they happened; the projection reads them in order to derive state.

9. Trust & Reliability — making reports trustworthy in Dhaka traffic

The hard problem: a report comes in. You can't send someone to verify it. How do you decide which reports to trust, which to dispatch teams to, and which to bulk-reject — without ever leaving the office? Answer: the phone captures trust signals automatically before the admin ever sees the report. Eleven signals, five user-facing mechanisms, three anti-abuse guards. The system pre-triages; the admin overrides.

9.1 — Trust signals (the 11 things the phone captures automatically)

T1
GPS pin → reverse-geocoded ward + nearest sensor_id
Is this in the same ward as an active sensor? Did that sensor already report?
T2
Distance from last sensor reading
Report 50m from a sensor that read clean 30 minutes ago → suspicious.
T3
Multiple reports from independent sources within a window
Two unrelated Anjalis in the same ward reporting the same hour → high signal.
T4
Reporter's own history
First-time reporter = medium trust. Reporter with 5 prior verified-true = high. Reporter with 2 prior verified-false = low.
T5
Photo of the water
A photo is harder to fake than text. Required for priority-queue routing.
T6
Photo EXIF (now + this device + this location)
Catches reused / downloaded photos. Reads GPS, timestamp, device from the image header.
T7
Voice note transcript
Natural language ("water is brown and smells bad") is harder to invent than a typed sentence. Recording adds liveness.
T8
Self-classified severity category
Bad smell / discoloration / sick person / visible contamination / pipe burst. Compared against photo + language — mismatch is a signal.
T9
Time of day
3 AM from a new user at a far-from-anything location = noise. 7 AM from a known school operator = gold.
T10
Recent activity at the exact GPS pin
Pin reported 6 hours ago and closed false-alarm → new report starts at low trust.
T11
Reporter phone number reputation
Same number reported 4 verified-false in 30 days → flagged (soft version, not Aadhaar).

9.2 — Five mechanisms that ride on top of the workflow

M1
Smart pre-triage — admin sees a trust band, not a raw report
highmediumlow High-confidence reports (T3 + T4 + T5/T6) go amber-first. Low-confidence (first-timer + no photo + 3 AM + near recent false-alarm) lands in the bulk-triage bucket for 30-second sweeps, not mixed with real ones. Admin's verify step becomes a 5-second "agree or override the band" decision instead of a 5-minute triage from scratch.
M2
Auto-acknowledge with credibility-weighted ETA
Anjali gets back: "Got it. We're treating this as high priority — a field team will be dispatched within ~30 minutes." vs. "Got it. We have your report. Because this is your first report and we don't have other matching signals, an admin will review it shortly." Honest expectations; rewards good reporters.
M3
Reporter-reputation badge visible to admin
🟢 trusted⚪ new🟡 caution Small badge next to the report in the verification pane. Not for auto-routing — admin still has the final say — but to focus attention.
M4
Geo-proximity cross-check with sensor reading
If the report's ward sensor last read clean 10 minutes ago, the verification pane shows: "Note: Ward 12 sensor last read normal 10 minutes ago. Reading was 0.21 NTU, threshold is 1.0." The sensor is the co-witness when it can be. Same UI when it agrees — the admin has the sensor + the human report pointing the same way → high confidence.
M5
5-minute hold-and-cluster window
Before notifying admins, the system holds the report for 5 minutes and watches for matching reports in the same ward. If 2+ reports cluster → confidence high → notify admins immediately with "2 matching reports in last 5 minutes" tag. Real incidents cluster; fakes don't. Cheap, powerful filter.

9.3 — Three anti-abuse guards (proportionate, explainable)

A1 — One-strike soft throttle
After 2 verified-false reports in 30 days, the user's reports go straight to the bulk-triage bucket, not the priority queue. Still allowed to report, just not prioritised.
A2 — Report-with-evidence minimum
To qualify for the priority queue, the report must carry at least one of: photo, voice note, or self-classified category matching the EXIF location. Bare text still goes through — to the bulk-triage bucket.
A3 — Verified-closure feedback loop (citizen confirms)
When Anjali gets the closure notification, she taps ✅ or ❌. ❌ triggers IncidentReopened{parent} on the chain — the closure is reversed, not silently lost. ✅ adds +1 to the verified-true count, raising future reputation.

9.4 — The architectural unlock

With these trust signals in place, the admin's verify step becomes much simpler. Today the verify step says "review source evidence, confirm real issue" — that's heavy cognitive load. With the trust band + sensor cross-check + reputation badge, the system does the triage; the admin does the override. High-band reports are 5-second decisions. Low-band reports in the bulk-triage bucket are 30-second sweeps. Medium-band reports get the focused review. The admin's role is unchanged — they still own the verify — but their time is spent where it matters.
